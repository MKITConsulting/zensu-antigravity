Such a fault therefore costs the anchor, never the mode — with the single exception of the registration timeout named below, which costs the whole injection. Every fault also **discloses** on stderr under a named class, because `none` is what a session with no chain armed legitimately renders too, so without a line a corrupt document, an unloadable module and a dead child are indistinguishable from ordinary healthy output. The blocking hazard that class of read carries is closed at the SOURCE: the shared reader now opens with `O_NONBLOCK`, so a FIFO or device planted at the document path — `.zensu/state/` is writable from inside the session — returns immediately and is rejected by the regular-file check instead of hanging a hook that fires on every prompt. The hook additionally `lstat`s the document before the read, which is what keeps that read from creating the state directory, and stands as defence in depth on the blocking half. The `timeout` on the registration is belt for neither: a hook killed at its deadline emits nothing at all, so that turn loses the whole directive — the anchor, the mode contract and the off-phrase branch — which is the one fault here not routed to `none`. It is a **20 s registration**, SIZED rather than inherited from the 1 sibling entries carrying 10: three bounded children are reachable in series on one invocation (the merged prompt-and-anchor child, the prompt-only recovery child and the off-phrase marker write, 5 s each — the recovery is gated on elapsed < 3 s, so the realized worst case is about 13 s of ladder budget rather than the full 15) on top of the `node` spawns paid before any of them, and at 10 the off-phrase path alone consumed the whole budget — killing the hook between the write child's `O_EXCL` open and its rename, so the marker never landed, the mode stayed on, and the could-not-deactivate branch never printed because the hook was dead. `ZEN_REGISTRATION_TIMEOUT_SOURCE_BUILD` in the hook header records the source-host build the sizing was derived on (2.1.260); native child timing is not inferred from that historical measurement. What the host does at that deadline, and whether it kills the process group or only the direct child, is unverified — the number is headroom over a computed worst case, never an observation of the deadline. See [zen-mode](../skills/zen-mode/SKILL.md), the *Anchor multi-step work* rule, for the full rule, which the row deliberately summarises rather than reproduces, and the never-compress carve-out for security warnings, irreversible actions, and credentials. It explicitly **overrides** any other compressed or telegraphic style mode for the duration. A skill is loaded once and fades after a handful of turns, which a low-capacity user is the least likely to notice — hence the per-prompt reminder. Resolution is three-valued, most specific first: the session marker (`${ZENSU_PROJECT_DIR:-.}/.zensu/state/zen-mode-<scv1-session-key>.json`, holding `{"active":true\|false}`), then `hooks.zenModeDefault` (itself defaulting to `true`). A symlinked marker or state directory, and a marker that does not spell out an active mode, both resolve to OFF — unreadable state must never impose the mode on a user who may have just left it. Deactivation is performed by the HOOK, not the model: a prompt carrying `zen off` / `zen-mode off` / `turn off zen` / `stop zen`, or consisting solely of `normal mode`, records `{"active":false}` directly, so the off-switch still works after the model has drifted — and the OFF context is emitted only once the write is confirmed. It **writes rather than deletes** on purpose: under the `true` default a removed marker would resolve straight back to active and trap the user in the mode. The marker is keyed by the resolved Session Control key **and** rooted at `zensu_resolve_project_dir` (the accessor the writer uses, not the host-native `ZENSU_PROJECT_ROOT`, which is a different namespace on Git Bash), so a session with a new key starts from the configured default, one that keeps its key keeps the mode, and a sibling session in the same project is unaffected. Symlinked markers are refused on both the read and the write side, and so is a present-but-non-regular one; a HARD LINK is not refused by either writer, deliberately — the landing publishes by `rename(2)`, which repoints the name and leaves any other link on the old inode untouched, so the destroy hazard is closed by the rename alone while refusing on the link count only cost the escape (one `ln` in the session-writable state directory used to make every later off-attempt fail, in-band and out-of-band alike). The in-band write is verified POSITIVELY — the marker must exist and record an inactive mode — so a write that never landed reaches the could-not-deactivate branch instead of scoring as success, and stale `<marker>.tmp-*` siblings older than five minutes are swept where the state directory is created. The out-of-band writer (`hooks/lib/zensu-zen-mode.sh`) runs under the same watchdog ladder, writes its whole buffer or fails, and exits 2/3/4 for a bad marker shape, a failed open-or-write and a failed rename so its shell layer names the cause instead of reporting every refusal as `cannot write`; its `--status` verb additionally consults `hooks.zenMode`, so a session whose hook is disabled is reported `off` with the flag named on stderr rather than `on`. Mode resolution runs before the prompt is ever read, so a session with the mode off never pays for prompt extraction; the hook is otherwise a no-op for non-main principals and under `zenMode:false`. The native host receives four dispatcher registrations, not this engine inventory.

After explicit approval of a saved implementation plan, the main thread applies the canonical
route question, naming the four mutually exclusive delivery routes: `/zensu-autopilot`,
`/zensu-tdd`, `/zensu-pilot`, and implementing directly. Keep the route ordering, recorded
preference and non-interactive restrictions of `plan-approved-delegate.sh`. This is a skill
procedure: PreInvocation does not fabricate a native ExitPlanMode approval event. Generic
code requests receive the separate two-choice TDD reminder, not this four-route question.

The standalone directive opens with a `ZENSU DELIVERY ROUTE:` field. It resolves the
`/zensu-delivery-route` marker before `hooks.defaultDeliveryRoute`; `tdd` or `direct`
answers the question without asking, while `ask` leaves the question open. An explicit
preference in the user's own approval message still wins for that plan. The four semantic
answers remain (1) Autopilot, (2) Zensu workflow, (3) Pilot and (4) implement directly,
ranked by the plan's fit as above. After answer (2) the model records the route through the
rendered helper command before dispatching `/zensu-tdd`, so once that call runs the
question is not asked again this session until `/zensu-delivery-route` changes the route.
A declined call records nothing and the question comes back; disclose that and still
perform the selected workflow. Answer (4) records nothing and decides only that plan.
The question must disclose these persistence rules before the answer. Never record a No
with `--direct` yourself: only the user's own session-route instruction authorizes that
marker. Other answers, explicit per-request preferences and already resolved routes record
nothing. Preserve a user's broader explicit instruction for the ongoing task without
converting it into a session marker.

For a generic code request, the reminder consults the `/zensu-delivery-route` marker,
then `hooks.defaultDeliveryRoute`, rendered as the `ZENSU DELIVERY ROUTE:` field at its
end. Ask only when the field reads `ask` and no explicit preference or other fast path
applies. A Yes is recorded through the rendered helper command, and a No records nothing
and decides only that request. Disclose that a Yes can be remembered through one shell
call requiring native permission, while a No is not remembered; a declined record call
leaves the question available next time. A typed preference decides that request and
records nothing. The generic reminder offers neither Autopilot nor Pilot. The record call
is `{session-helper} --helper delivery-route -- --tdd`, using the current bootstrap's
literal prefix in one standalone shell call. Claim persistence only after its observed
successful result; a failed call is not a recorded preference.

Model-facing state commands must use the exact session-helper prefix injected for the current
conversation. Raw helper examples below describe engine verbs; prefix them through
`--helper log --` (or the named helper), never manufacture private data paths or session selectors.

### Hook Opt-Out

Zensu ships thirty-five automatic hooks that fire across the development lifecycle (full enumeration in the [Hooks (35)](#hooks-35) table above). The configurable subset is listed below; `pre-edit-tdd-reminder.sh` has no on/off flag of its own — it is bypassed for the whole session via the `ZENSU_TDD_GATE` env var in the environment the host runtime starts with and passes through for whole sessions frozen into vanilla mode by `tddImplementation` (see that row below), and `session-start-evidence-discipline.sh`, `pre-write-plugin-data-guard.sh` and the browser consent pair `pre-browser-navigation-consent.sh` / `post-browser-navigation-consent.sh` have none by design (see [Evidence Discipline](architecture.md#evidence-discipline), [Plugin-Data Guard](gates.md#plugin-data-guard) and [Browser Consent Gate](gates.md#browser-consent-gate)). Any flagged hook can be disabled via `~/.zensu/config.json` without forking, editing, or uninstalling the plugin.

**Visible opt-outs (bypass ledger).** Env-var escapes stay free — no gate ever blocks on them — but they are no longer silent: while a TDD session is active (chain-state `active`), each gate records the escape it was bypassed through (`ZENSU_TDD_GATE`, `ZENSU_BASH_WRITE_GATE`, `ZENSU_MCP_GATE`, `ZENSU_SECRET_SCAN`, `ZENSU_CHAIN`, `ZENSU_EDIT_LANDING_GATE`, `ZENSU_REQUIREMENTS_GATE`, `ZENSU_FULL_SUITE_GATE`, `ZENSU_ACCEPTANCE_GATE` — env or inline prefix) into the per-session state file, deduplicated per gate name and carrying gate names only (never command payloads or values; entries are validated at write and read against a closed allowlist of those nine names plus the retired `ZENSU_TEST_WITNESS`, which stays readable so a ledger an older installation wrote still renders, pre-existing junk sanitized and bounded by the closed allowlist + per-name dedup). The ledger records gate escapes ONLY, so every name rendered under "Gates bypassed" is genuinely a gate that was escaped; operator interventions that are not escapes — notably the `/zensu-recover-chain` repair — record their provenance as a workflow `history` entry inside their own transaction instead of borrowing this surface. One recording semantic for every site: the escape is recorded when it short-circuits the gate's **decision point** — the zensu CLI gate records when a `zensu` invocation is actually present; `ZENSU_MCP_GATE` is also honored (and therefore also recorded) by the Bash source-write gate at its own any-Bash-command decision point while that opt-in gate is on, so it can appear in sessions that never ran the zensu CLI; the full-suite gate records at `--chain-done` only where it applies (a ticket-bound standalone terminus or a bound `pass`, in a git work tree, with the claimed ticket matching); the acceptance gate records at `--chain-done` on a ticket-bound standalone terminus with the claimed ticket matching, and never for a bound Autopilot chain, which it does not check; the secret-scan gate's inline escape records only on write-channel commands while its exported env escape records on the first scanned payload of any kind; `zensu-log.sh append` carries a SECOND `ZENSU_SECRET_SCAN` site with a semantic neither of those covers — it records whatever `ZENSU_SECRET_SCAN=off` reaches its OWN process environment — which includes an inline prefix written in front of the `append` command itself, since a shell assignment before a command is exported into it and the verb sees one environment either way — once per `append` invocation that takes it, and only while `ZENSU_SESSION_KEY` resolves (that verb carries no session bind of its own, so outside a Zensu-started session it records nothing); what it never records is a prefix on some OTHER command, because it does not consult the decider (R53 in `tests/structure/test-artifact-redaction.sh` is the pin, and it uses the inline spelling); inline prefixes are reported by the command parsers themselves (quoted spellings and mixed commands included; heredoc bodies, argument mentions, and channel-less commands excluded), and a command that ends up DENIED never mints a ledger entry from the denying gate — deny wins over markers WITHIN each gate (sibling hooks on the same tool call decide independently, so a gate that individually allowed may still have recorded its own escape even when another gate denied the call; over-reporting, never under-reporting). A config-disabled gate (`hooks.<flag>:false`, or an opt-in flag such as `hooks.bashWriteGate` that is not `true`) has no decision point — deliberate standing configuration is not ledgered. The chain-end summary surfaces the list as `Gates bypassed during this session: …` (`/zensu-autopilot` prints the build-level union into the PR body as `Gates bypassed during build: …`), sourced via `zensu-log.sh --bypass-list`, which is THREE-valued: the list; `none` — permitted only after it read a valid document that recorded no escape; or, on exit 3, an `UNREADABLE — …` line on stdout meaning the document could not be validated, which is explicitly NOT a clean ledger (a further non-zero exit, notably exit 2 for an unavailable session identity, leaves stdout empty and writes to stderr). `--bypass-note <gate>` is the write verb, itself scoped to active sessions. The ledger resets at every `--tdd-begin` and `--tdd-reset`, and BOTH echo any non-empty outgoing ledger as `previous-run bypasses (cleared now): …` so multi-run unions have a durable trace; recording is fail-open — a ledger failure never breaks the gate. **What the ledger does and does not prove.** It detects a DAMAGED document, not an authenticated deletion: `validateWorkflowState` is structural, and the `bypasses` array carries no MAC or monotone counter, so a document edited in place but left schema-valid still reads `valid` and renders `none`. Binding it would mean a new workflow-state field, which the Runtime Lineage rule makes a breaking minor — deliberately not paid for here. **This paragraph is the authoritative residual list; the skill and test surfaces point at it rather than restating it.** The releases that end a session without the chain-end report now render the line themselves, on the Stop hook's stderr — the operator channel every other release message there already uses: `ZENSU_CHAIN=off`, `hooks.chainEnforcer=false`, and the cap release after a chain fails to converge. The `--chain-done` verb renders it too, on the same channel, so the zero-change terminus discloses through either entry point — a gate escape needs no file change to be recorded. All four are silent only when the ledger is genuinely empty. What remains genuinely undisclosed is the schema-valid edited document above, and a ledger cleared by `--tdd-begin` or `--tdd-reset` — both of which echo the outgoing entries first, so the trace survives in the run log rather than in the report. Read the line as "what a readable document recorded", never as "no gate was escaped".

### Config Resolution Order

The plugin **deep-MERGES** the config files field by field to build the effective `config.json` — global as the base, the project-local file overlaid on top. Precedence, lowest to highest:

1. `$HOME/.zensu/config.json` (global base). Every key here applies unless a higher level overrides it.
2. `$ZENSU_PROJECT_DIR/.zensu/config.json` (project-local overlay). Wins **per key** over the global file; keys it does not set **fall through** to the global value. Auto-discovered — `ZENSU_PROJECT_DIR` is set by the host runtime for all hook subprocesses, no user setup required.
3. `$ZENSU_CONFIG` (environment override). When set, it is used **verbatim as a full override — no merge**, the explicit escape hatch for a single shell session.

A missing or malformed file is treated as `{}`, and any key absent from the merged result falls back to the hook's built-in default. So a downstream project can commit a project-local `.zensu/config.json` that sets only a few keys (e.g. enabling `autoFixIncludeSuggestions:true`) and the developer's other global settings still apply.

**Three keys deviate from this section.** `hooks.reviewerSpawnAutoAllow` and `hooks.subagentShell` are exempt from the merge and the per-key overlay, while `ZENSU_CONFIG` still replaces the global file and the project overlay outright. Both follow the `zensu_hook_enabled_strict` rules rather than the merged `cfg()` — the shell reader itself for `reviewerSpawnAutoAllow`, and a port of it inside the capability gate for `subagentShell` — because each governs a capability the plugin grants ITSELF rather than a protection it runs. There is no merge and no per-key overlay: a `false` in ANY candidate withdraws the grant, so a project-local file cannot re-arm one the user withdrew globally; a present-but-malformed candidate withdraws it instead of degrading to `{}`; and an empty candidate list withdraws it rather than falling back to the built-in default. Their rows above state the full rule. `hooks.sessionAutoAdopt` deviates in ONE respect: `false` is sticky across the layers, while an unreadable or malformed layer degrades to enabled as it does for every ordinary key, because enabled runs a repair rather than a bypass; its row above states that rule. No other key should be given either treatment without the same argument.

> If your project commits a `.zensu/config.json` and a developer also has `~/.zensu/config.json`, the two are **merged field by field** — the project-local file wins per key, and keys it omits keep the developer's global value. Use `ZENSU_CONFIG=/path/to/other.json` to bypass the merge entirely for one session.

### Log Timestamp Style

The `/zensu-tdd` workflow writes a session log under `.zensu/logs/YYYY-MM-DD-HHMM_tdd-<slug>.log` with one line per RED/IMPL/GREEN phase. The wall-clock prefix on each line can be reformatted or suppressed via `~/.zensu/config.json`:

| Style | Inline format | Example |
|---|---|---|
| `wall` (default) | `[HH:MM:SS]` | `[14:23:45] step1 RED test_isOdd — FAIL` |
| `relative` | `[+HH:MM:SS]` from session start (< 24h); `[+Dd HH:MM:SS]` for deltas ≥ 24h | `[+00:01:23] step1 RED test_isOdd — FAIL` / `[+1d 03:45:12] step42 GREEN test_persist — PASS` |
| `none` | no prefix | `step1 RED test_isOdd — FAIL` |

Filenames retain the `YYYY-MM-DD-HHMM` session timestamp for uniqueness across multiple sessions on the same day; only the inline log-entry prefixes are affected.

Example (relative timestamps):

```json
{
  "logging": {
    "timestampStyle": "relative"
  }
}
```

Invalid values, missing keys, malformed JSON, or a missing `node` binary all fall back to `wall`.

### Full-Suite Evidence

`zensu-log.sh --evidence-run` runs a test command itself and records the real exit code. A `full` or `scoped` run is also bound to a fingerprint of the project's working tree, taken together with the nested work tree it ran in when there is one, so a later edit makes the record stale. Records live in the plugin's private data directory (`$ZENSU_PLUGIN_DATA/evidence-run/v1/`): the file tools of the reviewer and of a neutral subagent cannot read them, the subagent shell guard denies them by name, and Edit/Write cannot reach them. A Bash redirect from the main thread, or an obfuscated subagent command, can still write them.

```bash
ZENSU_PLUGIN_DATA="<plugin data>" bash "<plugin root>/hooks/lib/zensu-log.sh" --evidence-run --scope full
```

| Argument | Effect |
|---|---|
| `--scope full\|lint\|build\|coverage\|scoped\|acceptance` | Required. `full`, `scoped` and `acceptance` fingerprint the working tree at start and end. A local chain's full-suite verdict reads only `full` runs; a chain whose full suite runs in CI reads its `scoped` runs too ([Full Suite in CI](#full-suite-in-ci)). An `acceptance` run is the observed evidence one acceptance record cites ([Acceptance Verification](#acceptance-verification)). |
| `--cmd '<shell>'` | The command to run. It runs from a private script file under `set -o pipefail` in `bash --noprofile --norc`, with stdin connected to the null device. It runs in the caller's working directory when that directory lies in the git work tree of the bound project root (for a root outside git: inside the root), and otherwise in the project root with a notice on stderr, because the tree fingerprint describes the project root. The plugin's own bindings (`ZENSU_SESSION_KEY`, `ZENSU_PLUGIN_DATA`, `ZENSU_PLUGIN_ROOT` and the rest of the Session Control exports) are removed from its environment, and `ZENSU_PROJECT_DIR` is the caller's own value. |
| `--show tail\|all` | `tail` (default) prints the last 80 lines once the run ends; `all` prints the whole output. The full output always stays in a private log file whose path is printed first, so a background run can be inspected while it runs. |
| `--if-stale` | With `--scope full`, skips the run when the newest `full` record is green on the current tree. With `--scope scoped`, skips it when the newest run of the same command is green on the current tree. |
| `--local` | Runs `--scope full` in a chain whose full suite runs in CI. Without it, such a run is refused with exit `2`, writes no record, and the refusal says it is not a suite failure. Pass it only when the user asked for a local full run. |
| `--log <run log>` | Appends one machine-authored `EVIDENCE RUN — scope=… exit=… duration=… tree=… record=… \| cmd: …` line to a TDD run log through the normal `append` path (secret scan and path redaction included). `--start <epoch>` feeds the `relative` timestamp style. |

The exit status is the command's own. A signal maps to `128 + n`, and a signal to the runner stops the whole process group and records the run as `interrupted`. A usage error, a refused command or an unavailable store exits `2`. The last output line is one summary: `zensu evidence-run: scope=… exit=… duration=…s tree=… record=… cmd=…`, with the command passed through the secret scan.

The tree fingerprint uses a temporary index, so the real index is never touched. `.zensu/` is excluded, so the run's own artifacts never make it stale. A `full` or `scoped` run whose command starts with a literal `cd <dir>` into a git work tree nested inside the project's own work tree, such as a worktree under `.agents/worktrees/`, is fingerprinted over the project and that work tree together (see [Full-Suite Gate](gates.md#full-suite-gate)). A cwd in such a work tree runs the command in the project root instead, as `--cmd` describes, and an `acceptance` run keeps the project's fingerprint. Over 20000 untracked files or 512 MiB of untracked content, or when `git` fails, the record carries no tree and names the reason. Retention keeps the newest 40 records per session and scope, so acceptance runs never evict a full-suite record, sweeps sessions idle for 14 days, and caps each output log at 5 MiB by cutting its middle.

| Key | Default | Effect |
|---|---|---|
| `evidence.fullSuiteCommand` | unset | The command `--scope full` runs when no `--cmd` is given. While it is set, an explicit `--cmd` that differs from it is refused, so every `full` record names the configured suite. Unset, `--scope full` needs `--cmd`. |
| `evidence.fullSuiteGate` | `required` | How `--chain-done` applies the full-suite verdict ([Full-Suite Gate](gates.md#full-suite-gate)): `required` refuses a missing, red, running, interrupted or stale record; `advisory` prints the same verdict marked `(advisory, not blocking)` and closes the chain. Any other value is treated as `required`, and the verdict says so. |
| `evidence.fullSuiteRunner` | unset | `ci` or `local`: the team-wide choice of where a chain's full suite runs, the last rank of the [Full Suite in CI](#full-suite-in-ci) ladder. `local` always wins. `ci` takes effect only while the CI pull-request pipeline is verified. Any other value is ignored. |
| `evidence.ci.workflow` | unset | The workflow file under `.github/workflows/` that runs the full suite on pull requests, for example `ci.yml`. Unset, the plugin picks the first workflow that triggers on `pull_request` and passes verification. |
| `evidence.ci.job` | unset | The job name pattern that runs the suite. `*` matches any text, so `test (*)` binds every matrix shard. Unset, the plugin proposes the job that looks most like a test run. |

```json

    "fullSuiteCommand": "npm test",
    "fullSuiteGate": "required"
  }
}
```

#### Full Suite in CI

A chain can leave its full suite to the repository's CI pull-request pipeline, so no full run happens on this machine. The tests affected by the change still run locally through `--scope scoped`, and the terminus closes as `FULL SUITE — deferred-ci` when every local test run on the current tree is green. The full suite then runs when a pull request is opened or updated. A red pull-request pipeline is possible, and the choice accepts it.

```bash
ZENSU_PLUGIN_DATA="<plugin data>" bash "<plugin root>/hooks/lib/zensu-log.sh" --full-suite-policy --refresh
```

The verb prints `full suite: ci`, `full suite: ask` or `full suite: local`, followed by the CI job, the command it runs, the local full-suite command, the age of the last pull-request run, whether the check blocks merges, the conditions found in the workflow, and who decided. `/zensu-tdd` runs it in Phase 0. On `ask`, an interactive chain asks the user once; a delegated or headless chain treats `ask` as `local`. `/zensu-full-suite` records the answer and reports the state with `--status`.

**Verified** means all of this holds for a GitHub.com repository: a workflow under `.github/workflows/` triggers on `pull_request` (`pull_request_target` never counts), the repository is not a fork, and a job matching the bound pattern concluded `success` or `failure` in a completed pull-request run of the last 30 days. `skipped` and `cancelled` jobs do not count. Whether the check blocks merges is read from branch protection and rulesets and shown, never required. Path filters, branch filters and the `if:` conditions of the bound job are shown, not evaluated. The verification uses `gh api` and is cached in `$ZENSU_PLUGIN_DATA/ci-contract/v1/`. `--refresh` reuses a proof younger than 24 hours and otherwise verifies again over the network. When that fails for a transient reason, such as no network or a missing or failing `gh`, the cached proof keeps counting for up to 7 days and the policy line names the failure. A refresh that finds the pipeline no longer qualifies removes the cached proof. Every other read uses the cache alone: a proof older than 24 hours is marked `(stale)`, and one older than 7 days no longer counts. An edit to the workflow file voids the proof at once. Other forges resolve to `local`.

**Precedence.** `local` in any rank wins at once. CI runs need a `ci` choice in some rank and a verified pipeline:

1. the session marker `.zensu/state/full-suite-<session>.json` (`/zensu-full-suite --ci|--local|--auto --session`);
2. the record for this clone in the plugin data directory, shared by every worktree of the clone (`/zensu-full-suite --ci|--local|--auto --repo`);
3. `evidence.fullSuiteRunner` in the config.

With nothing recorded and a verified pipeline, the state is `ask`. A process inside CI (`CI`, `GITHUB_ACTIONS`, `GITLAB_CI`, `TF_BUILD` or `BUILDKITE`) never defers the suite to itself. `--tdd-begin` records the chain's runner in a snapshot, and the terminus honours CI only when the chain began with it: a switch to CI takes effect with the next chain, while a switch to local applies at once. Without a verified pipeline the chain runs the full suite locally, exactly as before, and the policy line names the reason. When a chain that chose CI closes locally, the terminus prints `FULL SUITE — local runner | <reason> | decided by: <rank>`.

**Not covered.** A full-suite command the model runs by hand is not blocked; only the runner refusal and the skill text steer it. The chain does not wait for CI, and nothing makes the branch reach a pull request. Autopilot gates still run their own test gate locally. The per-clone record and the snapshot live in the plugin's private data directory, which a Bash redirect from the main thread, or an obfuscated subagent command, can still write.

### Acceptance Verification

Every active `AC-###` criterion of a standalone chain's plan is verified live before the chain
closes ([Acceptance Verification Gate](gates.md#acceptance-verification-gate)). `/zensu-tdd`
Phase 6 step 6d and `/zensu-self-review` drive it through `/zensu-verify-feature --chain`, which
records one verdict per criterion:

```bash
ZENSU_PLUGIN_DATA="<plugin data>" bash "<plugin root>/hooks/lib/zensu-log.sh" --acceptance-status --log <run log>
ZENSU_PLUGIN_DATA="<plugin data>" bash "<plugin root>/hooks/lib/zensu-log.sh" --acceptance-record --ac AC-001 --verdict pass --driver browser --log <run log> <<'EVIDENCE'
Opened the settings page, saved the value, reloaded and saw it again.
EVIDENCE
```

| Argument | Effect |
|---|---|
| `--ac <AC-###>` | The criterion. It must be an active `AC-###` row of the plan this session's edit-landing receipt names; an unknown, `FR-###` or deprecated id is refused. |
| `--verdict pass\|fail\|partial` | `partial` means the criterion could not be proven here, and it blocks like `fail`. |
| `--driver <name>` | One of the nine driver ids of `/zensu-verify-feature`. `api`, `cli`, `async`, `iac`, `custom` and `library` are observed: they need `--evidence-run` unless the verdict is `partial`. `browser`, `mobile` and `desktop` are attested. The spellings of earlier releases stay accepted, so a running session whose skill text still names them can record: `desktop-native` is attested and `artifact` is observed. A `desktop` record is stored as `desktop-native`, the spelling every earlier installation still reads, because after an update both installations can read the same session's records. |
| `--evidence-run <er1 id>` | An `--evidence-run --scope acceptance` record of this session. It must have completed on the current tree without changing it, and its exit code must agree with the verdict. |
| `--log <run log>` | Required for both verbs. Its stem must equal the run log this session's edit-landing receipt records. `--acceptance-record` appends one `ACCEPTANCE — …` line to it. |
| stdin | The evidence text, at most 2000 characters, in English whatever language the conversation is in, because up to 200 characters of it land in the run log. It is refused when empty or when it matches a secret pattern, and paths are redacted before it is stored. |

`--acceptance-status` prints one `ACCEPTANCE STATUS — …` line plus one line per criterion and
exits 0 only when every active criterion passes on the current tree. The summary line ends with
the remedy segments a `--chain-done` refusal would print (`run:`, `fix:`, `add:`, `restore:`);
act on the segment, never on the exit code alone, because verifying an unchanged tree again
cannot turn a failing criterion. Records live in
`$ZENSU_PLUGIN_DATA/acceptance-verify/v1/records/`; retention keeps the newest 20 records per
criterion and 400 per session, and sweeps sessions idle for 14 days.

| Key | Default | Effect |
|---|---|---|
| `evidence.acceptanceGate` | `required` | How `--chain-done` applies the acceptance verdict: `required` refuses while an active criterion lacks a `pass` on the current tree; `advisory` prints the same verdict marked `(advisory, not blocking)` and closes the chain. Any other value is treated as `required`, and the verdict says so. |

## Native environment and authority

The model does not inherit trusted plugin/session environment selectors from hooks.
Use `session-helper.sh --session <conversation-id> --helper <name> -- <arguments>` exactly
as injected. The wrapper pins private data, executed root and canonical host session internally.
`--stdin-file <absolute-file>` transports bounded structured input with an exact content hash.

`ZENSU_SHIM_TRACE` enables the shipped shim's three-column invocation trace.
`ZENSU_SHIM_DECISIONS` enables decision/hash witnesses for live probes. They are opt-in and
never supply session authority. `ZENSU_SESSION_TOKEN` is the inherited work-order credential;
helper arguments must never contain its value.

The config and evidence opt-outs above retain their canonical scope and visible bypass ledger.
A model cannot use a caller-supplied session/root/plugin-data variable to redirect a bound command.
Native reanchor refuses missing ownership proof; source-host environment files, desktop receipts
and shared session-id pointers are not used. See [session control](session-control.md).
